## 第二轮（同日）：修指标语义 —— 用户拍板从这项开始

### 先拿到硬证据，再动手
用 `sqlite3 db/dev.db` 直接读（`updatedAt`/`createdAt` 是毫秒时间戳，要 `/1000`）：
- `cmvp1gg5` DELIVERED：墙钟跨度 `updatedAt-createdAt` = 296s，但 `latencyMs` = 26628ms → **只覆盖 9%**
- `cmvohhnh` HUMAN_REVIEW：959s vs 365738ms → **只覆盖 38%**
→ "latencyMs 低估"从推测变成实测。

### 踩到的坑：`updatedAt` 被迁移污染，不能用来算"陈旧度"
5 条老数据的 `updatedAt` 全等于 `2026-09-17 09:16:57`（那次批量迁移一次性改写了它们）。
原计划用"时间戳陈旧度"回溯找被放弃的任务，**这条路走不通**。
要么改用 `executionLogs` 里最后一条的时间戳，要么把 2026-09-17 当硬分界线。

### 根因
- `latencyMs` 只有一个写入点，在 **SCAD_GENERATED 转换块内**（`execute-cad-job.ts:876`）。
  **DELIVERED 那次写入（:1355）根本不带 latencyMs**，所以成功任务的字段值是"到 SCAD 生成为止"。
- `llmCallCount` 只有一个写入点，是**绝对值赋值**，值来自 `generationResult.model_execution.call_count`
  （只统计生成 skill 自己那一次）。漏掉 intake / request-research / 编译修复 / 视觉修复，
  且每次 run 都**覆盖**前一次的总数。
- 附带发现：`job-store.ts:143` 的 `incrementLlmCallCount()` 是**返回 0 的空壳**，全仓无人调用。已删。

### 修法（关键决策：在"咽喉点"计数，而不是在 5 个调用点各插一次）
- **所有** LLM 调用最终都经过 `createChatCompletionDetailed`（`model-router.ts:412`）：
  intake / request-research / 视觉修复走 `createChatCompletionWithFallback` → 它 → ；
  编译修复 / 生成 skill 直接调它。所以在它入口 `countLlmCall()` 一次，
  新增任何调用点都会自动被统计，不会有人忘记。
- 计数器用 `AsyncLocalStorage`。**用 `run()` 包，不能用 `enterWith()`**：
  `enterWith` 改的是当前 async resource 的 store，函数返回后计数会**泄漏给调用方**，
  于是同一个调用方之后启动的兄弟任务会共用一个计数器——正是这个指标要防的污染。
  实现办法是给 `executeCadJob` 加一层薄包装（`withLlmCallMeter(() => runCadJob(...))`），
  避免为了包作用域去缩进 1200 行。
- `latencyMs` 移进 `finally` 块，**全文件只有一处写入**；`llmCallCount` 改为
  `{ increment: delta }` 增量刷新（并发下不会互相覆盖，重复写也不会重复计数）。
- 视觉修复是**独立的 HTTP 请求**，在 pipeline 作用域之外，单独包一层。
- 口径切割脚本 `scripts/reset-metrics-baseline.ts`（`bun run metrics:reset`，默认 dry-run，
  加 `-- --yes` 才真跑）：清空两列，保证之后任何非空 `latencyMs` 都是新口径。
  因为两个修正都只让数值**变大**，新旧行混在一列里根本分不出来，平均数是无意义的。
  **已在 db 副本上验证，原 `db/dev.db` 未动**（副本 11 行被清空，原库 2 行仍在）。
